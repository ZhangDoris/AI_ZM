# 匹配优先级控制 · 功能规格文档（PRD）

> 版本：v2.0 ｜ 状态：草稿 ｜ 适用范围：智能预筛系统 · 管理员端
> 双层模型：① **项目层（方案编号）**——管理员可打可选优先级标签（重点/优先/普通/未设置），仅作标记、**不参与**匹配顺序，是"设置重点项目"的配置入口。② **患者层（匹配任务）**——真实匹配发生在患者层面（字段：患者编号/患者缩写/方案编号/操作时间）；系统按**并发阈值（默认 10 条）**控制同时匹配数量，超出部分**按操作时间 FIFO 排队**；队列有空闲位自动补位；**特别着急的患者可手动「立即匹配」加急**（在阈值之上额外执行，不打断在跑的匹配）。
> 配套原型：`匹配优先级控制-原型.html`（双层：项目列表做优先级设置 + 患者匹配队列承载阈值/FIFO/加急；默认阈值 10）。

---

## 1. 问题陈述（Problem Statement）

智能预筛系统按"方案编号"将受试者/患者匹配到研究项目。匹配动作消耗有限的系统与人力的并发能力。

- **谁遇到**：系统管理员、运营人员，在匹配高峰期（多中心同时入组、批量导入）几乎每天遇到。
- **表现**：大量项目同一时刻并发发起匹配，系统负载陡增、响应变慢甚至超时；管理员缺乏对"谁先匹配、谁稍等"的可控手段，只能被动等待。
- **不解决的代价**：系统不稳定 → 运维与客诉成本上升；无法对紧急项目做快速干预。
- **证据假设**（待补真实数据）：高峰期并发匹配数峰值远超平稳期；管理员需要"容量闸门 + 排队 + 加急"三件套来稳定系统并保留人工干预权。

---

## 2. 目标（Goals）

| # | 目标（Outcome） | 如何衡量成功 |
|---|----------------|--------------|
| G1 | 系统并发可控：同时匹配数**不超过阈值太多**，高峰不雪崩 | 高峰匹配超时/失败率下降 ≥ 50% |
| G2 | 超额患者匹配任务**公平、可预期**地按操作时间排队，不抢跑、不随机 | 队列顺序与操作时间顺序一致率 100% |
| G3 | 管理员对紧急患者有**手动加急**能力，且**不打断**在跑的匹配 | 手动「立即匹配」成功率 100%，在跑匹配 0 中断 |
| G4 | 优先级标签为**可选**，不打标签也能正常匹配与排队 | 未设置标签的患者匹配任务匹配成功率 = 设置标签项目 |
| G5 | 管理员能直观看到实时并发、阈值、队列与标签分布 | 配置/监控任务完成率 ≥ 95%，单次 < 3 分钟 |

**用户目标**：系统稳定可控，紧急患者随时能加急，其余按先来后到公平排队。
**业务目标**：稳定性提升、紧急诉求可快速响应、降低运维介入成本。

---

## 3. 非目标（Non-Goals / Scope）

1. **不做基于优先级的自动抢跑**：重点/优先标签**不参与**排队先后顺序（已确认）。标签仅作识别。
2. **不做基于时间段的限流**（如高峰窗口）。本期仅以"并发阈值"做容量闸门。
3. **不做匹配算法质量优化**（打分）。本期只控制调度顺序与并发闸门。
4. **不做跨组织并发配额**（按中心/客户分配预算）。本期全局单一阈值。
5. **不做多级审批流**：标签与加急由管理员直接操作，无需审批。

---

## 4. 用户角色

- **系统管理员（Primary）**：设定并发阈值；在「项目匹配列表」给方案编号打/清优先级标签（可选）；监控实时并发与队列；对紧急患者手动「立即匹配」；标记在跑患者匹配任务「完成」。
- **运营人员（Secondary，只读）**：查看实时并发、阈值、队列与标签分布，向合作方解释为何某患者暂未匹配（P1 可选）。

## 5. 核心概念

| 概念 | 说明 |
|------|------|
| **方案编号（项目层）** | 项目唯一业务标识（如 `FA-2026-001`）。项目层**仅做优先级标签配置**；患者匹配任务通过方案编号关联到项目。 |
| **可选优先级标签** | 管理员可打 `重点 / 优先 / 普通`，也可`未设置`。**仅作标记，不参与**患者匹配排队顺序。 |
| **患者匹配任务（患者层）** | 真实匹配的单元：含 患者编号、患者缩写、方案编号、操作时间；是并发阈值与排队的计量对象。 |
| **并发阈值 N（默认 10）** | 系统最多同时匹配的患者条数。超过即进入待匹配队列。 |
| **实时并发匹配数** | 当前"匹配中"的患者匹配任务数量（含手动加急项）。 |
| **待匹配队列（FIFO）** | 患者匹配任务超过阈值时，按**操作时间**先进先出排队；有空闲位时队首自动补位。 |
| **手动「立即匹配」** | 对队列中紧急患者加急，**在阈值之上额外执行**（突破容量），不打断在跑匹配。 |

> **关键规则（已确认）**：
> 1. 优先级标签**可选**：可设可不设；设了也不改变患者匹配排队先后。
> 2. 触发：**实时并发达到阈值（默认 10）** → 后续患者匹配任务进入 FIFO 队列。
> 3. 释放：在跑的患者匹配任务「完成」后，队列队首自动补位。
> 4. 加急：紧急患者可手动「立即匹配」，在阈值之上额外跑，不中断他人。

## 6. 用户故事（User Stories）

- **US1（P0）**：作为管理员，我想**可选地**给方案编号打/清优先级标签（重点/优先/普通），以便识别重要项目（但不需要它来决定顺序）。
- **US2（P0）**：作为管理员，我想设定**并发匹配阈值**（默认 10），以便控制系统同时匹配的数量。
- **US3（P0）**：作为管理员，我希望超过阈值的患者匹配任务**自动按操作时间 FIFO 排队**，而不用手动干预、也不抢跑。
- **US4（P0）**：作为管理员，我希望在跑的患者匹配任务完成后队列**自动按序补位**，不残留、不卡死。
- **US5（P0）**：作为管理员，我想对队列中**特别着急的患者**手动「立即匹配」加急，且**不打断**正在进行的匹配。
- **US6（P0）**：作为管理员，我想在一个控制台看到实时并发、阈值、队列内容、标签分布，掌握全局。
- **US7（P1）**：作为运营人员，我想只读查看上述状态，向合作方解释为何某项目暂未匹配。
- **US8（P2）**：作为管理员，我想按时间段设置不同阈值或限流窗口，增强调度灵活性。

## 7. 功能需求（Requirements · MoSCoW）

### P0 · Must Have

**FR-1 项目层：可选优先级标签（按方案编号）**
- 「项目匹配列表」中，管理员可在行内下拉或批量给方案编号设置标签：重点 / 优先 / 普通 / 未设置（即"设置重点项目"入口）。
- 标签**不影响**患者匹配与排队顺序；未设置标签的患者匹配任务照常参与匹配与排队。
- *验收*：Given 某方案设为"重点"或"未设置"；When 触发患者排队；Then 患者匹配任务在队列中均严格按操作时间排序，标签不改变位置。

**FR-2 并发阈值配置（默认 10）**
- 管理员可设定全局并发匹配阈值 N，默认值 10，范围校验 1–200。
- 保存即时生效。
- *验收*：Given 阈值 10；When 同时匹配患者数达到 10；Then 第 11 个患者匹配任务进入队列。

**FR-3 实时并发监控**
- 持续统计"匹配中"数量，展示实时并发、阈值、队列长度、标签分布。
- *验收*：Given 10 个匹配中、阈值 10；Then 看板显示"并发 10 / 10 · 排队 N"。

**FR-4 患者层：自动 FIFO 排队 + 患者匹配队列视图**
- 患者匹配队列视图字段：**患者编号、患者缩写、方案编号、操作时间、状态（匹配中/排队中）、操作（立即匹配 / 完成）**。
- 实时并发 ≥ 阈值时，新的患者匹配任务进入待匹配队列，按**操作时间**先进先出。
- 已匹配中的患者不被强制中断；有空闲位时队首自动补位。
- *验收*：Given 阈值 10、10 个匹配中、又来 3 个；When 观察队列；Then 3 个按操作时间先后排第 1/2/3 位；When 1 个完成；Then 队列第 1 位自动转为匹配中。

**FR-5 患者层：手动立即匹配（加急）**
- 管理员可对队列中任意患者「立即匹配」，使其在阈值之上**额外**执行，**不打断**在跑匹配。
- 加急项完成后，正常容量与队列恢复原有逻辑。
- *验收*：Given 队列有患者且容量已满；When 点击其「立即匹配」；Then 该患者变为匹配中、实时并发变为 11（>阈值），其余在跑患者不受影响；When 其完成；Then 实时并发回落，队列按序补位。

**FR-6 监控看板与日志**
- 控制台展示：实时并发、阈值、排队数、标签分布（如当前重点项目列表）。
- 提供关键事件日志：进入队列、自动补位、手动加急、完成（时间 + 患者编号 / 方案编号）。
- *验收*：Given 发生一次加急与一次补位；Then 日志包含对应两条记录。

### P1 · Should Have

- **FR-7 只读视图**：运营人员可查看状态（无编辑/加急权限）。
- **FR-8 阈值预警**：接近阈值（如 ≥ 80%）时给出预警提示。
- **FR-9 批量到达/导入**：支持批量导入触发匹配，统一按到达时间入队。

### P2 · Future / Won't（this time）

- **FR-10 时间段阈值/窗口**：按时间设置不同阈值或限流窗口（见 US8）。
- **FR-11 分中心/分客户配额**：按组织维度分配并发预算。
- **FR-12 优先级加权**：若未来需让标签影响顺序，引入加权 FIFO（本期不做）。

## 8. 成功指标（Success Metrics）

**领先指标（上线 1–4 周）**
- 高峰匹配超时/失败率下降 ≥ 50%（对比上线前同期）。
- 队列顺序与操作时间顺序一致率 = 100%。
- 手动「立即匹配」成功率 = 100%，在跑匹配中断数 = 0。
- 未设置标签的患者匹配任务匹配成功率 = 设置标签项目（验证"可选"）。
- 管理员监控/配置任务完成率 ≥ 95%，单次 < 3 分钟。

**滞后指标（上线 1 季度）**
- 因"匹配延迟/系统不稳定"产生的客诉/工单下降 ≥ 30%。
- 紧急患者平均加急响应时间 < 1 分钟（从点击到进入匹配）。
- 系统高峰期可用性 ≥ 99.5%。

**测量方式**：从匹配调度服务埋点（匹配发起/完成事件、并发计数、队列进出、加急事件）抽取，按日/周聚合；评估时点：上线后 1 周、1 月、1 季度。

## 9. 验收标准（Acceptance Criteria）

- [ ] 管理员可在「项目匹配列表」按方案编号设置/清除 重点/优先/普通 标签，**也可不设置**。
- [ ] 标签**不改变**患者匹配与排队顺序（验证 FIFO 优先于标签）。
- [ ] 管理员可配置并发阈值，默认值 10，保存即时生效。
- [ ] 实时并发 ≥ 阈值 → 后续患者匹配任务自动按操作时间进入队列。
- [ ] 在跑的患者匹配任务完成后，队列队首**自动按序补位**。
- [ ] 患者匹配队列视图展示：患者编号、患者缩写、方案编号、操作时间、状态、操作（立即匹配/完成）。
- [ ] 手动「立即匹配」可使队列中的患者在阈值之上加急执行，且**不打断**在跑匹配。
- [ ] 控制台可见：实时并发、阈值、排队数、标签分布、队列顺序。
- [ ] 关键事件（入队/补位/加急/完成）有日志记录，可追溯。
- [ ] 移动端管理界面可查看状态（配置/加急交互可降级）。

## 11. 时间与排期考虑

- **硬依赖**：匹配调度服务需暴露"匹配发起/完成"事件与实时并发计数（工程前置）。
- **建议分期**：
  - 一期（P0：FR-1~FR-6）：可选标签 + 阈值 + 自动 FIFO 排队 + 手动加急 + 看板/日志。
  - 二期（P1：FR-7~FR-9）：只读视图、预警、批量导入。
  - 三期（P2）：时间段阈值、分中心配额。
- 无明确合同/合规死线；建议跟随下一管理端迭代发布。

---

> **一句话总结**：用"可选标签 + 一个并发阈值（默认 10）+ FIFO 排队 + 手动加急"，把匹配调度变成"先来后到公平排队、紧急随时加急、系统稳定可控"的自动驾驶模式。
